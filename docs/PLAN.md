# 项目范围与架构约定

## 目标和交付边界

在 2–4 周内做出可演示、可测试的核心网关，展示异步请求处理、路由、共享限流、故障切换和数据持久化能力。工期是目标，功能是否完成以验收结果为准。

当前已实现本地 Demo，具体能力和接口见 [DEMO.md](DEMO.md)。本文保留 PostgreSQL / Redis 生产目标；Demo 使用 SQLite 与模拟上游，不等于下列生产能力全部完成。

### 核心 MVP

- OpenAI 兼容的 Chat Completions 和 Models 接口，同时支持非流式与 SSE。
- 一个 OpenAI 兼容上游适配器，可配置多个供应商或本地服务。
- 优先级、权重、有限次数故障切换和短期熔断。
- 虚拟 API Key 鉴权、按 Key 的 RPM、按上游的共享并发限制。
- PostgreSQL 请求记录、上游尝试、耗时和 Token 用量。
- React 只读监控页，以及 Docker Compose 演示、故障测试和压测报告。

### 后续完整管理台

保留用户约定的 Login、Providers、ModelRoutes、VirtualKeys、RequestLogs、Usage、Settings 页面规划。供应商、路由、Key 的在线编辑和管理员登录在核心链路稳定后实现；目录存在不代表功能完成。

预算计费、复杂 RBAC、SSO、更多原生供应商协议和 OpenTelemetry 留到后续。首版使用模块化单体，不引入 Celery、Kafka 或 Kubernetes。

## 请求链路

```text
调用方 → 虚拟 Key 校验 → RPM 限流 → 创建请求记录
       → 选路 / 熔断检查 → 获取上游并发租约 → HTTPX 调用
       → 返回 JSON / SSE → 记录尝试与结果 → 释放租约
```

- 配置运行时以 PostgreSQL 为准；bootstrap 环境配置只负责幂等初始化，不能在每次启动覆盖管理员后续修改。
- HTTPX 客户端复用连接池。数据库事务分段提交，不跨越整个上游响应生命周期。
- 虚拟 API Key 只保存可校验的哈希与展示前缀；上游真实 Key 使用环境主密钥加密后存储。
- 默认不记录提示词、完整请求体、响应正文或任何密钥。
- 管理员身份与模型调用虚拟 Key 独立；核心阶段管理接口使用独立的环境管理令牌，完整管理台阶段实现登录流程。

## 路由与失败行为

- 优先选择可用上游中优先级最高的一组，同组按正权重随机选择。
- 每次请求最多尝试 3 个不同上游；仅连接错误、上游超时、429 和 5xx 可触发切换，其他上游 4xx 直接结束。
- 客户端断开立即停止后续尝试，关闭上游连接，并释放当前请求持有的租约。
- SSE 向客户端发送第一个响应字节后不再切换；中途故障记录为流式中断，不伪造成功结束。
- 超时后切换仍可能发生上游重复执行或计费；逐次记录尝试，不承诺 exactly-once。
- 默认同一上游连续 3 次可重试失败后熔断 15 秒；半开只允许一个跨进程探针。
- RPM 和并发额度用 Redis Lua 原子更新。并发租约使用唯一标识、TTL 和续租，释放必须验证所有者。
- 本地 RPM 或所有候选上游并发额度耗尽返回 429；没有健康候选返回 503，错误体采用 OpenAI 风格。限流返回有依据的 `Retry-After`。
- PostgreSQL 或 Redis 在请求准入前不可用时返回 503，避免绕过鉴权或限制。执行中故障的记录和恢复行为列入集成验收。

## 数据记录

核心实体为 `virtual_api_keys`、`providers`、`model_routes`、`gateway_requests`、`upstream_attempts`；路由与上游的关联在数据库建模阶段实现。

- 请求记录保存 request ID、Key ID、公开模型名、最终状态、耗时、输入与输出 Token、错误类型。
- 每次上游尝试单独保存上游 ID、状态码、耗时与切换原因。
- 上游未提供 usage 时，Token 记录为未知，不当作零；只展示供应商实际报告的用量。
- 关键状态同步短事务写入；聚合指标可查询计算，不依赖内存后台任务保证日志可靠性。
- 进程崩溃可能留下未完成请求，需要识别为异常未完成，不能自动推断已成功、未计费或直接重放。

## 实施原则

先完成单上游请求，再增加路由和分布式状态；只有一个适配器时不预建注册框架。每一阶段提供可运行的验证场景，性能数字在同一环境测量后才写进 README。
